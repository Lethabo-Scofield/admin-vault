# Task: Streamline the public credential verification page

Update the public credential verification page to remove information already contained in the certificate and recommendation letter, while keeping verification status and document access prominent.

## Scope

Modify only:

`app/verify/[code]/page.tsx`

Do not change the database, API routes, credential-generation logic, or document templates.

## Current public routes

* `GET /verify/[code]` — server-rendered verification page.
* `GET /api/public/credentials/[token]` — public credential JSON.
* `GET /api/public/credentials/[token]/certificate` — certificate PDF.
* `GET /api/public/credentials/[token]/certificate-preview` — certificate PNG preview.
* `GET /api/public/credentials/[token]/letter` — recommendation-letter PDF.

The page already retrieves credential data server-side using `getPublicCredentialByToken(token)`.

## Required page structure

For a valid `PUBLISHED` credential, display these four sections in order:

### 1. Verification hero

Display:

* Clear “Verified” status
* Intern’s full name
* Credential number
* Current credential status

The verification result must be the most visually prominent element.

### 2. Certificate preview

When `hasCertificatePreview` is true:

* Display the certificate PNG prominently.
* Preserve its aspect ratio.
* Ensure it works responsively on mobile and desktop.
* Provide appropriate accessible alternative text.

When no preview exists, omit this section without showing a broken image or empty container.

### 3. Document actions

Show consistent primary actions side by side where space permits:

* **Download Certificate (PDF)**
  Route: `/api/public/credentials/[token]/certificate?download=1`
  Show only when `hasCertificatePdf` is true.

* **Download Recommendation Letter (PDF)**
  Route: `/api/public/credentials/[token]/letter?download=1`
  Show only when `hasLetterPdf` is true.

Stack the buttons on smaller screens. Remove the prominent “view letter in browser” action; if retained, make it a clearly secondary link.

### 4. Skills demonstrated

Keep the existing skills display because this information does not appear in either document.

* Preserve the chip-based presentation.
* Hide the entire section when there are no skills.
* Do not render an empty card.

## Remove from the page

Remove these standalone sections because they repeat information available in the certificate or letter:

* Internship dates
* Position or department
* Issue date and issuer
* Projects and responsibilities
* Founder recommendation
* Manager recommendation

Do not remove these fields from the database, APIs, certificate, or recommendation letter.

## Status handling

Preserve the existing revoked and not-found experiences.

For credentials that are missing, revoked, or otherwise not `PUBLISHED`:

* Do not show the certificate preview.
* Do not show document-download actions.
* Do not show skills.
* Clearly communicate the applicable status.
* Do not expose private or unnecessary credential data.

## Technical requirements

* Preserve `noindex`.
* Preserve `no-store` and all existing cache-prevention behaviour.
* Continue using server-side credential retrieval.
* Gate every document element using:

  * `hasCertificatePreview`
  * `hasCertificatePdf`
  * `hasLetterPdf`
* Keep existing secure token-based routes.
* Maintain the current visual design system and reusable components.
* Do not introduce new dependencies.
* Ensure responsive and accessible behaviour.
* Do not invent fields, routes, or flags that are not present in the codebase.

## Acceptance criteria

The implementation is complete when:

* A published credential shows its verification result, certificate preview where available, valid document buttons, and skills.
* Redundant detail and recommendation cards no longer appear.
* Missing document assets do not create broken or empty UI.
* Revoked and not-found credentials cannot access document or skills sections.
* Existing metadata and cache protections remain unchanged.
* The project passes its existing type-check, lint, and relevant tests.

After implementing, provide a concise summary of the changes and identify any checks that could not be completed.
